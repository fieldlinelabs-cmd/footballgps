## 1. アプリ概要

**FootballGPS** は、Apple Watch で GPS ベースのサッカートレーニングデータを記録し、iPhone で可視化・分析するアプリ。

| 項目 | 内容 |
|------|------|
| プラットフォーム | iOS (iPhone) + watchOS (Apple Watch) |
| アーキテクチャ | SwiftUI + HealthKit + CoreLocation + CoreMotion + WatchConnectivity |
| データ永続化 | UserDefaults (JSON エンコーディング) |
| 認証/バックエンド | 未実装 (Firestore 対応の dictionary プロパティのみ準備済み) |

### 3.2 GPSPoint / GPSData
**ファイル:** `ModelsTrainingSession.swift`

| プロパティ | 型 | 説明 |
|-----------|-----|------|
| `timestamp` | `Date` | 記録時刻 |
| `latitude` / `longitude` | `Double` | GPS 座標 |
| `speed` | `Double` | 速度 (m/s)。`CLLocation.speed` の負値は 0 に補正 |
| `altitude` | `Double` | 高度 (メートル) |
| `horizontalAccuracy` | `Double` | 水平精度 (メートル) |

`GPSData` は `sessionId` と `[GPSPoint]` の配列をまとめた JSON 保存用コンテナ。

### 3.3 AgilityEvent / AgilityData

**ファイル（新規）:** `ModelsTrainingSession.swift`（既存ファイルに追記）

アジリティ（急停止・切り返し）の発生記録を表すモデル。Watch 側で CoreMotion が検出した各イベントを iPhone に転送し、GPS 座標と紐付けてフィールド上にプロットする。

```
AgilityData (Codable)
├── sessionId: String          // 対応する TrainingSession.id
└── events: [AgilityEvent]

AgilityEvent (Codable)
├── timestamp: Date            // 検出時刻（Watch 計測。GPS 点との紐付けに使用）
└── magnitude: Double          // 3軸合成加速度ノルム（G 値）
```

**GPS 座標への紐付け（iPhone 側）:**
`AgilityEvent.timestamp` に最も近い `GPSPoint.timestamp` を検索し、そのフィールドローカル座標 `(x, y)` を取得してフィールド上にプロットする。

> **位置精度の限界:** GPS は `distanceFilter=2m` 設定のため、急停止直後は選手が 2m 移動するまで次の GPS 更新が来ない。また 5.5 m/s のスプリント中でも GPS 更新間隔は約 0.36 秒。アジリティ発生時刻と最近傍 GPS 点の時刻差は最大 0.4〜2 秒になり得る。結果として **マーカーの表示位置は実際の切り返し地点から最大 2〜5m ズレる可能性がある。** ★マーカーはおおよその発生エリアを示す参考表示として扱うこと。

**転送フォーマット:** GPSData と同様に `AgilityData` として Watch → iPhone に WatchConnectivity 経由で送信する。セッション終了時に `GPSData` とともに転送ペイロードに含める。

### 3.4 Field
**ファイル:** `ModelsField.swift`

| プロパティ | 型 | 説明 |
|-----------|-----|------|
| `corners` | `FieldCorners` | フィールド 4 隅の GPS 座標 (topLeft/topRight/bottomRight/bottomLeft) |
| `dimensions` | `FieldDimensions` | 実寸 (`length` x `width` メートル)。標準値: 105m x 68m |

**主要ロジック:**

- **`convertToFieldCoordinate(_:)`**: GPS 座標をフィールドローカル座標 (0~width, 0~length) に変換。平行四辺形座標系で連立方程式を解く。フラットアース近似 (`metersPerLat=110540`, `metersPerLon=111320*cos(lat)`) を使用。
- **`contains(coordinate:)`**: Ray Casting Algorithm でフィールド内外判定。
- **`matchRate(for:)`**: GPSPoint 配列に対するフィールド内一致率を返す。(フィールド選択画面での参考表示用)
- **`correctToRectangle(...)`** (static): ユーザーが指定した 4 点を最小二乗フィットで直角長方形に補正。重心・長辺方向の平均・直交する短辺方向を計算。

- `UserProfile`: Firebase Auth UID ベース。

## 4. 計測ロジック (Apple Watch)

### 4.1 WorkoutManager
**ファイル:** `WatchWorkoutManager.swift`

#### 4.1.1 HealthKit 連携

| 項目 | 詳細 |
|------|------|
| ワークアウトタイプ | `.soccer` / `.outdoor` |
| 共有権限 | `HKWorkoutType` |
| 読取権限 | `heartRate`, `activeEnergyBurned`, `distanceWalkingRunning`, `workoutRoute` |
| セッション管理 | `HKWorkoutSession` + `HKLiveWorkoutBuilder` |

> **注意:** `HKLiveWorkoutBuilderDelegate.didCollectDataOf` のコールバック内でデータ抽出処理は未実装。心拍数・歩数・消費カロリーは権限要求のみで、実際の値は取得していない。

#### 4.1.2 GPS 記録ロジック

```
CLLocationManager 設定:
  - desiredAccuracy: kCLLocationAccuracyBest
  - distanceFilter: 2m (2メートル移動ごとに更新)
  - activityType: .fitness
  - allowsBackgroundLocationUpdates: コメントアウト (要実機設定)
```

**記録フロー:**

1. `locationManager(_:didUpdateLocations:)` でロケーション受信
2. **精度フィルタ**: `horizontalAccuracy < 50m` の場合のみ採用
3. `GPSPoint` に変換して `gpsPoints` 配列に追加
4. 前回ロケーションとの `CLLocation.distance(from:)` で累積距離を加算
5. `CLLocation.speed` (>= 0) を現在速度・最高速度に反映

#### 4.1.3 サッカー指標の導出状況

| 指標 | 実装状況 | 導出方法 |
|------|---------|---------|
| 総走行距離 | **実装済** | CLLocation 間の逐次距離加算 |
| 現在速度 | **実装済** | `CLLocation.speed` (m/s) |
| 最高速度 | **実装済** | 速度の最大値を保持 |
| 平均速度 | **実装済** | `totalDistance / elapsedTime` |
| スプリント回数 | **iPhone側で実装予定** | Watch 側計算は削除。`SessionDataManager.saveSession()` で GPSData から計算して保存 |
| アジリティターン数 | **未実装** | Watch 側で CoreMotion（50Hz）検出 → AgilityData として転送 → iPhone 側で保存 |
| アジリティ強度スコア | **未実装** | iPhone 側で AgilityData から算出（0〜100、最大 G 値 or 上位5イベント平均 G 値ベース） |
| 心拍数 | **未実装** | `heartRate` プロパティは存在するが HealthKit からの読取なし |
| 歩数 | **未実装** | HealthKit 権限に `distanceWalkingRunning` はあるが未使用 |
| カロリー | **未実装** | HealthKit 権限に `activeEnergyBurned` はあるが未使用 |
| 移動軌跡 | **実装済** | GPSPoint 配列として記録、iPhone 側で可視化 |
| ヒートマップ | **実装済** | iPhone 側で GPSPoint をフィールド座標に変換しグリッド集計 |

#### 4.1.4 スプリント判定基準

iPhone 側の `SessionDataManager.saveSession()` で GPSData から計算する。

| パラメータ | 値 | 意味 |
|-----------|-----|------|
| 開始閾値 | 5.56 m/s（時速 20.0 km）以上 | アマチュア・部活・ジュニアユースの平均走力を考慮 |
| 最低継続時間 | 1.0 秒以上 | 瞬間的な GPS 飛びによる誤検知を排除 |
| 終了閾値 | 4.0 m/s（時速 14.4 km）以下 | ヒステリシスで同一スプリント区間を継続 |

**計算方式:** `GPSPoint` 配列を時系列順に走査し、上記条件を満たす連続区間を1回のスプリントとしてカウント。区間の開始・終了インデックスを `SprintSegment` として保持し、FieldPositioningView でのハイライト描画に利用する。

```
SprintSegment (Codable)
├── startIndex: Int     // gpsPoints 内の開始インデックス
├── endIndex: Int       // gpsPoints 内の終了インデックス
├── maxSpeed: Double    // 区間最高速度（m/s）
└── distance: Double    // 区間走行距離（m）
```

`TrainingSession.sprintCount` には区間数の合計を格納する。`SprintSegment` の配列は GPSData から毎回再計算して生成する（永続化しない）。`SessionDataManager.getGPSData(for:)` でロードした GPSData を `computeSprintSegments(_:)` ヘルパーに渡し、ビュー表示前に算出する。スプリント判定は純粋関数のため再計算コストは無視できる。

#### 4.1.5 シミュレーター対応

`#if targetEnvironment(simulator)` で分岐:

- HealthKit Workout Session の作成をスキップ
- 2秒間隔のタイマーで疑似 GPS ポイントを生成
- ランダムウォーク + 方向/速度変更 (5回に1回)
- フィールド範囲 (150m) 内にバウンド制約

## 4.2 加速度センサー連携（CoreMotion）

### 4.2.1 目的

GPS（2m 移動ごとに OS から通知。速度に応じて更新頻度が変動し、静止時は通知なし）では捉えられない「一瞬の急ブレーキ・切り返し（アジリティ）」を、Apple Watch 内蔵の加速度センサー（50Hz）で補完計測する。手首装着特有の腕振りノイズを数理フィルタで除去し、プレー中の純粋なアジリティ動作のみを検出する。

### 4.2.2 センサー設定

| パラメータ | 値 | 備考 |
|-----------|-----|------|
| サンプリング周波数 | 50 Hz（0.02秒間隔） | `CMMotionManager.deviceMotionUpdateInterval = 1/50` |
| 取得データ | 重力補正済み3軸加速度 | `CMDeviceMotion.userAcceleration`（ジャイロ＋加速度センサー融合）を使用。`CMAcceleration`（raw）は静止時でも重力の 1G が乗るため**使用しない** |
| 動作タイミング | ワークアウト記録中のみ | `startWorkout()` で開始、`endWorkout()` で停止 |

> **実機確認が必要な前提条件:** watchOS での `CMDeviceMotion` 50Hz 連続サンプリングが `HKWorkoutSession` のバックグラウンド実行中も維持されるかは、Apple の公式ドキュメントに保証の明示がない。実機テスト（特に画面消灯・手首を下げた状態）での動作確認を実装前に行うこと。50Hz が維持できない場合は 25Hz への引き下げを検討する。

### 4.2.3 フィルタリング（3段階）

#### ステップ 1: 3軸合成（方向ニュートラル化）

`CMDeviceMotion.userAcceleration`（重力補正済み）の3軸を合成し、装着向きに依存しない衝撃の絶対値を算出する。

```
let ua = deviceMotion.userAcceleration  // 重力を除いた動的加速度
magnitude = √(ua.x² + ua.y² + ua.z²)  [単位: G]
// 静止時 ≒ 0G、鋭い切り返し時 ≒ 1.5〜3.5G
```

> `CMAccelerometer.acceleration`（raw）は静止時に常時 1G（重力）が加算されるため使用しない。raw を使うと普通に走るだけで閾値を超える誤検知が多発する。

#### ステップ 2: 腕振り周期運動の除去

猛ダッシュ時の規則的な腕振り（低周波の正弦波）を取り除き、急停止・切り返し時の突発的な衝撃スパイク（高周波成分）のみを抽出する。

```
実装方法: ハイパスフィルタ（時定数 α ≒ 0.8 程度）
  filtered[t] = α × (filtered[t-1] + magnitude[t] - magnitude[t-1])
```

> **一時停止・再開時のリセット必須:** 一時停止中は CoreMotion を停止する。再開時にフィルタの内部状態（`filtered[t-1]` と `magnitude[t-1]`）を 0 にリセットしてから再開すること。リセットなしで再開すると、停止前後の magnitude 差がスパイクとして誤検知される。

#### ステップ 3: GPS速度によるコンテキスト制限

キック・スローイン・静止時の激しい腕の動きを誤検知しないよう、GPS 速度で有効範囲を制限する。

```
アジリティ判定を有効化する条件:
  GPS speed ≧ 3.0 m/s（ジョギング以上の移動中のみ）
```

### 4.2.4 アジリティターン判定基準

| パラメータ | 値 | 意味 |
|-----------|-----|------|
| 衝撃閾値 | **2.5 G 以上**（暫定） | `userAcceleration` ノルム基準。鋭い急停止・切り返しと判定。実機テスト後に調整 |
| GPS速度条件 | ≧ 3.0 m/s | 走行中のみ有効（静止・低速時は除外） |
| カウント方法 | スパイクの立ち上がり1回につき1カウント | 連続超過中は追加カウントしない |

> **閾値は暫定値。** `userAcceleration` 前提での 2.5G は概ね妥当だが、選手の体格・床面（芝・土・体育館）・プレースタイルで実測値がばらつく。実機テストでログを取り、誤検知・未検知のバランスを確認してから確定させること。

**検出時の記録:** `AgilityEvent(timestamp: Date, magnitude: Double)` を生成し、メモリ上の配列に追加する。

### 4.2.5 アジリティ強度スコアの算出（iPhone 側）

セッション受信後、`AgilityData.events` の G 値から 0〜100 のスコアを算出する。

```
方式A（最大値ベース）:
  score = clamp((maxMagnitude - 2.5) / (upperBound - 2.5) × 100, 0, 100)

方式B（上位5イベント平均ベース）:
  top5avg = events.sorted(by: magnitude).prefix(5).average
  score = clamp((top5avg - 2.5) / (upperBound - 2.5) × 100, 0, 100)

upperBound の初期値: 6.0G（暫定）
```

> **上限値 `upperBound` は暫定値。** 6.0G はサッカーでの最大衝撃の目安として設定したが、実測に基づかない値である。実機テストで複数選手のデータを収集し、上位 95 パーセンタイル程度の値を上限として再設定すること。方式A/Bの採用もテスト後に決定する。

### 4.2.6 データ転送

セッション終了時、`GPSData` と同一ペイロードに `AgilityData` を追加して Watch → iPhone へ転送する。

```json
{
  "type": "trainingSession",
  "session": { ... },
  "gpsData": { ... },
  "agilityData": {
    "sessionId": "UUID文字列",
    "events": [
      { "timestamp": 1234567890.123, "magnitude": 3.2 },
      ...
    ]
  }
}
```

## 5. データの連続性 (一時停止・再開・バックグラウンド)

### 5.1 ワークアウトライフサイクル

```
[開始画面] ──(開始)──> [記録中] ──(一時停止)──> [一時停止中]
                         │                         │
                         │                    (再開) │
                         │ <────────────────────── │
                         │
                    (終了確認) ──> [サマリー画面] ──(完了)──> [開始画面]
```

| 状態遷移 | isRunning | isPaused | GPS記録 | タイマー | HKSession |
|---------|-----------|----------|---------|---------|-----------|
| 開始 | `true` | `false` | `startUpdatingLocation` | 動作中 | `.running` |
| 一時停止 | `true` | `true` | `stopUpdatingLocation` | 停止 | `.paused` |
| 再開 | `true` | `false` | `startUpdatingLocation` | 動作中 | `.running` |
| 終了 | `true`* | `false` | `stopUpdatingLocation` | 停止 | `.ended` |
| サマリー閉じる | `false` | - | - | - | - |

> *終了時に `isRunning` を即座に `false` にしない設計。サマリー画面表示のため `showingSummary` で制御し、ユーザーが「完了」ボタンを押した時点で `isRunning = false` + `reset()`。

### 5.2 バックグラウンド動作

| 項目 | 現状 |
|------|------|
| `allowsBackgroundLocationUpdates` | **コメントアウト** (実機テスト時に有効化が必要) |
| Info.plist `UIBackgroundModes` | 未設定 (要: `location`, `workout-processing`) |
| HKWorkoutSession | 実機ではバックグラウンド継続が可能 (watchOS の仕様) |

> **課題:** 現在のコードではバックグラウンドでの GPS 記録が無効。実機で試合中に手首を下げると記録が途切れる可能性がある。

### 5.3 経過時間の計測

- `Timer.scheduledTimer` で 1 秒間隔カウントアップ
- 一時停止時にタイマーを `invalidate`、再開時に再作成
- **一時停止中は `elapsedTime` が加算されない** (実効プレイ時間のみ計測)

## 6. データ転送 (Watch -> iPhone)

### 6.1 転送フロー

```
[Watch] endWorkout()
    │
    ├── 実機: WatchConnectivityService.sendSession()
    │     ├── isReachable ? sendMessage (即時) : transferUserInfo (キューイング)
    │     └── sendMessage 失敗時 -> transferUserInfo にフォールバック
    │
    └── シミュレーター: UserDefaults に直接保存
          └── pendingSession_{id}, pendingGPS_{id}, pendingSessionIds
```

### 6.2 iPhone 側受信

**`PhoneWatchConnectivityService`** が以下を処理:

1. `didReceiveMessage` (リアルタイム) / `didReceiveUserInfo` (キューイング) で受信
2. `type == "trainingSession"` を検証
3. `TrainingSession` + `GPSData` を辞書からパース
4. `SessionDataManager.saveSession()` で永続化 (`fieldId` は未設定のまま保存)
5. ユーザーが iPhone のセッション詳細画面でフィールドを手動選択して紐付け

## 7. データ永続化

### 7.1 SessionDataManager

### 9.1 FieldPositioningView (移動軌跡 + アニメーション再生)
**ファイル:** `ViewsFieldPositioningView.swift`

- GPS ポイントをフィールド座標に変換し、`Path` で線描画（全軌跡を常時表示）
- **スプリント区間**: 通常軌跡（青い線）のうち `SprintSegment` に含まれる区間を**赤色の太線**で上書き描画
- **アジリティマーカー**: `AgilityEvent` の GPS 座標紐付け結果を ★ アイコンでフィールド上にピン留め
- 開始地点: 緑丸 + "START"、終了地点: 赤丸 + "END"
- **選手ドット**: `currentPointIndex` で指定された座標に青丸（直径12 + 白ボーダー直径18）を描画。タイムラインに沿ってリアルタイムに移動する
- **アジリティ通過エフェクト**: 選手ドットが ★ マーカー座標の近傍（半径 5m 以内）を通過した瞬間に、ドットを一時的に拡大→縮小させるパルスアニメーションを発火する
- フィールド背景: 緑色 + 白ラインで外枠/センターライン/センターサークル/ペナルティエリア/ゴールエリアを描画
- アスペクト比維持 (長辺を縦に自動配置)
- `isFlipped = true` の場合、全座標を 180度回転して描画 (§9.4 参照)

**引数:**

| 引数 | 型 | 説明 |
|-----|----|------|
| `gpsData` | `GPSData` | GPS データ（変更なし） |
| `field` | `Field` | フィールド情報（変更なし） |
| `isFlipped` | `Bool` | コート入れ替えフラグ（変更なし） |
| `currentPointIndex` | `Int` | 選手ドットを表示するポイントのインデックス。`0` = セッション開始位置 |

### 9.1.1 時系列アニメーション再生コントロール
**ファイル:** `ViewsSessionDetailView.swift`（`positioningView(field:)` 内）

`FieldPositioningView` の下に再生コントロールパネルを配置する。

**コントロールパネル構成:**

```
┌─────────────────────────────────────────────┐
│  00:00 / 90:12                        [8x ▼]│  時刻表示（現在/総時間）+ 速度メニュー
│  ─────────●────────────────────────────────  │  タイムラインスライダー
│  [⏮]   [−10s]       [▶]       [+10s]   [⏭] │  再生ボタン群
└─────────────────────────────────────────────┘
```

**ボタン動作:**

| ボタン | アイコン | 動作 |
|------|---------|------|
| 先頭へ | ⏮ | 先頭（00:00）に移動。再生は停止 |
| 10秒戻る | −10s | 実時間 10 秒前に移動（再生速度に依存しない） |
| 再生/一時停止 | ▶ / ⏸ | 再生と一時停止をトグル |
| 10秒進む | +10s | 実時間 10 秒後に移動（再生速度に依存しない） |
| 末尾へ | ⏭ | 末尾に移動。再生は停止 |

**再生速度（デフォルト: 8x）:**

| 速度 | 90分セッション換算 |
|-----|----------------|
| 1x | 90分 |
| 2x | 45分 |
| 4x | 約22分 |
| **8x** | **約11分** |
| 16x | 約5.5分 |

**スライダー操作:** ドラッグ中は再生を一時停止。離した時点の位置から再開。

**再生終了時の挙動:** 末尾に達したら先頭（00:00）に自動的に戻り、停止状態になる。

**初期状態:** ポジショニングタブを開いたとき、`currentTime = 0`（先頭）、`isPlaying = false`（停止）。

### 9.2 FieldHeatmapView (滞在密度)
**ファイル:** `ViewsFieldHeatmapView.swift`

- グリッドサイズ: 40列 × 28行（長さ方向 × 幅方向）
- GPS ポイントをフィールド座標に変換し、ガウシアンカーネル（sigma=1.5セル ≈ 4m半径）で周囲セルにも重みを分散させてグリッドに加算
- 対数正規化（最大値 = 1.0）後、4段階グラデーション:
  - `0`: 透明（未訪問エリアはフィールドの緑が見える）
  - `0〜0.25`: 青系（低頻度）
  - `0.25〜0.5`: シアン系
  - `0.5〜0.75`: 黄系
  - `0.75〜1.0`: 赤系（最頻出エリア）
- 不透明度は `intensity × 0.85`（強度ゼロで完全透明、最大で 85%）
- `.blur(radius: 6)` でセル境界のブロック感を解消し、なめらかなグラデーション表示を実現
- 90度回転表示（ゴールが上下）
- `isFlipped = true` の場合、全座標を 180度回転してグリッドに配置（§9.4 参照）
- 詳細仕様: 技術実装仕様書 §10 参照

### 9.3 サード別滞在分析

#### 概要

既存の 40列 × 28行 ヒートマップグリッドを応用し、ピッチの長軸方向（105m）を3等分した「ディフェンシブ / ミドル / アタッキングサード」ごとの滞在 GPS 点数比率（%）を算出・表示する。

#### サード定義

ピッチ長軸（`Field.dimensions.length`）を3等分する。グリッドの長さ方向は 40列に対応するため、各サードは約 13〜14 列になる。

| サード | 意味 | フィールド座標（長軸 y） | グリッド列（概算） |
|-------|------|---------------------|----------------|
| ディフェンシブサード | 自陣（ゴール前） | `0 〜 length/3` | 0 〜 13 |
| ミドルサード | 中盤 | `length/3 〜 length×2/3` | 14 〜 26 |
| アタッキングサード | 敵陣（相手ゴール前） | `length×2/3 〜 length` | 27 〜 39 |

#### 算出方法

ヒートマップの生成と同じ GPSPoint → フィールドローカル座標変換を使用する。グリッドは別途生成せず、変換後の `y` 座標をそのままサード判定に利用する。

```
defensiveCount  = GPSPoints で y < length/3       の点数
middleCount     = GPSPoints で length/3 ≦ y < length×2/3 の点数
attackingCount  = GPSPoints で y ≧ length×2/3     の点数
total           = defensiveCount + middleCount + attackingCount

defensiveRatio  = defensiveCount  / total × 100  [%]
middleRatio     = middleCount     / total × 100  [%]
attackingRatio  = attackingCount  / total × 100  [%]
```

#### `isFlipped` との連動

`isFlipped = true`（コート入れ替え）の場合、座標変換で `y` が反転するため、ディフェンシブサードとアタッキングサードのラベルも入れ替える。計算式やグリッド構造の変更は不要。

```
isFlipped = false:  下ゴール = 自陣（ディフェンシブ）
isFlipped = true:   下ゴール = 敵陣（アタッキング）→ ラベルを入れ替えて表示
```

#### 表示仕様

**ヒートマップ画面オーバーレイ:**
- フィールド長軸の 1/3・2/3 の位置に白い破線を引き、3つのゾーンを視覚的に区切る
- 各ゾーンの中央に `"守備 XX%"` / `"中盤 XX%"` / `"攻撃 XX%"` をラベル表示（白字・小フォント）

**統計タブ:**
- 守備 / 中盤 / 攻撃の3色の横棒グラフで比率を表示

#### 実装対象ファイル

| ファイル | 変更内容 |
|---------|---------|
| `ViewsFieldHeatmapView.swift` | サード境界破線のオーバーレイ追加。各サード % ラベル表示。`isFlipped` 連動でラベル反転 |
| `ViewsSessionDetailView.swift` | 統計タブにサード別比率バー追加 |
| `SessionDataManager.swift`（またはビュー内） | `computeThirdRatios(gpsData:field:isFlipped:) -> (defensive, middle, attacking)` ヘルパー追加。派生値のため永続化不要、表示時に計算 |

### 9.4 コート入れ替え機能

#### 概要

サッカーは前半・後半でコートが入れ替わるため、セッション全体を通してポジショニングを重ね合わせると攻守が逆転した状態になる。ユーザーが表示を見て違和感を感じた場合に手動で反転できる。

#### 動作仕様

| 項目 | 仕様 |
|------|------|
| 操作 | ポジショニング・ヒートマップタブの「コート入れ替え」ボタンをタップ |
| 反転変換 | フィールド座標 `(x, y)` → `(width - x, length - y)` (フィールド中心を軸とした 180度回転) |
| 切替回数 | 無制限 (タップのたびにトグル) |
| 状態の共有 | ポジショニングとヒートマップで `isFlipped` を共有。どちらで操作しても両タブに反映 |
| 永続化 | `TrainingSession.isFlipped` として UserDefaults に保存。セッションを閉じて再度開いても状態を維持 |
| 統計タブへの影響 | なし (距離・速度はフィールド座標に依存しない) |

#### ボタン表示

```
[↔ コート入れ替え]  ← isFlipped = false のとき
[↔ コート入れ替え ✓] ← isFlipped = true のとき (反転中であることを示すマーク)
```

#### 将来対応: 時間帯分割方式 (案2) ※保留

> 現状は全 GPS ポイントを一律反転する方式を採用。将来的には、前半・後半など時間帯ごとに反転区間を指定し、各ポイントを個別に変換する「時間帯分割方式」への拡張を検討する。これにより、前半は A 方向・後半は B 方向の実際の移動位置を正確に重ね合わせた分析が可能になる。
>
> **保留理由:** アマチュアサッカーでは試合時間が毎回異なるため（前半20分の練習試合もあれば40分の公式戦もある）、「どの時刻から反転するか」をユーザーにどう入力させるかの UI 設計が未確定。入力方式（スライダーで境界時刻を指定する / セッション記録中に手動でフラグを立てる など）を別途検討してから着手する。

## 12. 設計上の前提・制約

1. **単一ユーザー前提**: 認証未実装のため `userId` は固定値。マルチユーザー対応は Firebase Auth 導入後。
2. **オフライン優先**: データは端末ローカル (UserDefaults) に保存。クラウド同期は未実装。
3. **GPS 精度依存**: フィールド座標変換はフラットアース近似。赤道付近や極地では誤差が大きくなるが、サッカーフィールド規模では問題なし。
4. **Watch -> iPhone 一方向**: データは Watch で記録 -> iPhone に転送の一方向フロー。iPhone から Watch への指示送信は未実装。
5. **フィールド登録が前提**: ヒートマップ・ポジショニング表示にはフィールドの 4 隅 GPS 座標登録が必須。未登録時は案内画面を表示。
