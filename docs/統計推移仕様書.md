## 1. 背景と目的

今のプレイヤーデータで比べられるのは「今回 vs 直近5回平均」と「直近5回平均 vs 自己ベスト」だけで、数ヶ月単位の成長は見えない。また、ポジションによって求められる動きが違うのに、全セッションが同じ平均に混ざっている。

**目的:**
- 過去1・3・6・12ヶ月のデータをグラフで見て、長い目で自分の成長を確認できるようにする
- 「今日の出来は、過去と比べてどうだったか」をすぐ確認できるようにする
- ポジション別に絞り込み、同じポジションのセッションどうしで比べられるようにする

## 2. 現状の整理

| 項目 | 現状 | 本仕様での扱い |
|---|---|---|
| セッションのポジション | 保存していない。AI監督の入力欄にあるだけで、フィードバック生成にしか使わない | セッションごとに保存する（§4） |
| プロスタイル診断のポジション判定 | ヒートマップの空間類似度で CF／ウイング／センターハーフ／CB／SB の5分類を判定する。**AIは使わない（端末内の計算）**。詳細画面を開いたときにだけ計算し、保存しない | 同じ仕組みに GK を加えて自動推定に使う（§5）。表記を7分類にそろえる（§5.7） |
| スタミナ（`staminaDrop`）・高強度割合（`hrIntensityRatio`） | セッション詳細を**初めて開いたときにだけ**計算・保存する。開いていないセッションは nil | 一括計算で埋める（§7） |
| `sprintCount` | 記録時点の閾値の値が残っていることがある。詳細を開くと現在の閾値で計算し直して同期する | 一括計算で同期する（§7） |
| 試合／練習の区別 | なし | **区別しない**。記録するのは練習試合か試合だけという前提（§14） |

## 3. 方針サマリー

- ポジションは **FW／WG／MF／CB／SB／WB／GK の7分類**とし、セッション（ドリル）ごとに1つ持たせる
- ポジションは**プロスタイル診断と同じヒートマップ類似度で自動推定**して設定する。違っていればユーザーが手動で直す。手動で直した値は、その後の自動処理で上書きしない
- 推定のために、GK の**ポジション推定専用テンプレート**を追加する（プロスタイル診断のタイプ一覧には出さない）
- **WB はヒートマップでは SB・WG と見分けられないため、自動推定の結果には出さない。** 直近に手動で WB を設定していれば、SB・WG の推定結果を WB として扱う（§5.3）
- プロスタイル診断のポジション表記を7分類にそろえ、SB は「SB（WB）」、WG は「WG（WB）」と表示する（§5.7）
- 新しい指標として「**ポジションの高さ**」（平均の高さ・最前線の高さ）を追加する。全ポジション共通の指標で、GK専用の評価は作らない
- 推移画面（プレイヤーデータタブから開く）で、期間（1M／3M／6M／12M）×ポジションで絞り込んだ推移グラフと成長サマリーを見せる
- セッション詳細に「**今日の出来**」カードを置き、そのセッションを同じポジションの過去のセッションと比べる
- 新しい永続化ストアは作らない。`TrainingSession` に任意（Optional）のフィールドを足し、集計は都度計算する（プレイヤーデータと同じ方針）

## 4. ポジション

### 4.1 分類

| 値 | 表示名 | 含むもの |
|---|---|---|
| `FW` | FW | センターフォワード、セカンドトップ |
| `WG` | WG | ウイング、サイドハーフ（4-4-2など） |
| `MF` | MF | ボランチ、アンカー、インサイドハーフ、セントラルMF、トップ下 |
| `CB` | CB | センターバック |
| `SB` | SB | サイドバック（4バックの両サイド） |
| `WB` | WB | ウイングバック（3バック・5バックの両サイド） |
| `GK` | GK | ゴールキーパー |

ポジション選択画面では、表示名と一緒に「含むもの」を補足文として出す。

### 4.2 データモデル

`TrainingSession` に次の2つを追加する。どちらも Optional で、旧データは nil のまま読み込める。

```swift
var position: PlayingPosition?            // 集計・表示に使うポジション。nil = 未設定
var positionSource: PositionSource?       // .auto = 自動推定 / .manual = ユーザーが設定
var estimatedPosition: PlayingPosition?   // ヒートマップから推定した生の結果（WB にはならない）。nil = 推定できなかった・まだ推定していない
```

`position` は、`positionSource == .manual` ならユーザーが選んだ値、`.auto` なら `estimatedPosition` に §5.3 の WB ルールを適用した値になる。生の推定結果を別に持つのは、手動の設定が変わったときに、GPS データを読み直さずに WB ルールを適用し直せるようにするため。

```swift
enum PlayingPosition: String, Codable, CaseIterable {
    case fw = "FW", wg = "WG", mf = "MF", cb = "CB", sb = "SB", wb = "WB", gk = "GK"
}
enum PositionSource: String, Codable {
    case auto, manual
}
```

**型の置き場所:** `ModelsTrainingSession.swift` は Watch アプリのターゲットとも共有している。`TrainingSession` のフィールドに使う型なので、`PlayingPosition`・`PositionSource` も同じファイルに定義する（iPhone 専用ファイルに置くと Watch 側のビルドが通らなくなる。`DrillBreakInterval` と同じ扱い）。

### 4.3 編集 UI

- **セッション詳細:** ヘッダー付近に「ポジション: MF（自動）」のようなチップを置く。タップすると選択シートを開く
  - 7分類のどれかを選ぶと `position` に設定し、`positionSource = .manual` にする
  - 「自動推定に戻す」を選ぶと `positionSource = .auto` にし、その場で推定し直す（推定できなければ nil）
  - どちらの操作のあとも、§5.3 の WB ルールを全セッションに適用し直す（手動の設定が変わると、後のセッションの結果が変わりうるため）
  - 未設定のときは「ポジション: 未設定」と表示する
- **セッション一覧:** 各行にポジションの小さなバッジを出す（未設定なら出さない）
- **AI監督フィードバック:** ポジション入力欄が空なら、セッションのポジションの表示名（例: 「MF」）を初期値として入れる。ユーザーが書き換えた内容が優先で、AI監督側の保存内容は変えない

## 5. ポジションの自動推定

### 5.1 推定方法

プロスタイル診断のステップ1（ヒートマップの空間類似度）と同じ方法を使う。

1. セッションのヒートマップ（28×40グリッド、`computeHeatmapGrid`）を作る。向きは `isFlipped` を反映する
2. 各テンプレートの理想ヒートマップとのコサイン類似度を計算する
3. ポジションごとに類似度の最大値を取り、最も高いポジションを `estimatedPosition` とする

テンプレートとポジションの対応は次のとおり。`ProStyle.category` は §5.7 で `PlayingPosition` 型に変えるので、そのまま使える。

| テンプレート | 推定するポジション |
|---|---|
| `ProStyle.all` のうち category = `.fw`（旧 CF） | FW |
| category = `.wg`（旧 ウイング） | WG |
| category = `.mf`（旧 センターハーフ） | MF |
| category = `.cb` | CB |
| category = `.sb` | SB |
| **GK テンプレート（新規・推定専用）** | GK |

WB のテンプレートは作らない。WB は高さで見ると SB と WG の中間を動くポジションで、ヒートマップでは SB・WG のどちらとも見分けられないため。

### 5.2 推定専用テンプレート（GK）

既存の `generateIdealHeatmap` は、守備・中盤・攻撃の3つのゾーン中心（行 4.5／13.5／22.5）にガウス分布を置く方式で、GK の「ゴール前だけに集中する」分布を表せない。そこで推定専用テンプレートは、**縦方向の中心と幅を直接指定できる**形で定義する。

```swift
struct PositionTemplate {
    let position: PlayingPosition
    let rowCenters: [(row: Double, weight: Double)]  // 縦方向の分布中心（row=0: 自陣ゴールライン, 27: 敵陣ゴールライン）
    let sigmaRow: Double
    let lateralBias: Double   // ProStyle と同じ意味（0=中央, 1=サイド）
    let sigmaCol: Double
}
```

初期値（実データで調整してよい）:

| | 縦方向の中心（重み） | sigmaRow | lateralBias | sigmaCol | 意図 |
|---|---|---|---|---|---|
| GK | 行1.0（1.0） | 1.8 | 0.0 | 4.0 | 自陣ゴール前の狭い範囲に集中する |

横方向の重みは `generateIdealHeatmap` と同じ式（中央とアウトサイド左右対称の混合）を使う。

GK は分布が特徴的なので、高い精度が見込める。

### 5.3 WB ルール

WB の選手が毎回 SB・WG から手で直さなくて済むように、`positionSource == .auto` のセッションの `position` を次のように決める。

```
estimatedPosition が SB または WG で、
かつ そのセッションより前の日時のセッションのうち positionSource == .manual のもので最も新しいものの position が WB
  → position = WB
それ以外
  → position = estimatedPosition
```

- 一度 WB に直せば、それより後のセッションは自動で WB になる
- ほかのポジションに手動で直せば、それより後のセッションにはルールが働かなくなる（ポジションが変わった選手にも対応できる）
- 推定結果が MF・FW・CB・GK のときは、ルールを適用しない（WB の選手でもヒートマップがはっきり違えば、その推定を信じる）
- 適用し直すのは `estimatedPosition` と日時だけで決まる計算なので、GPS データは読み込まない。適用し直すのは、手動の設定が変わったとき（§4.3）と、新しく推定したとき（§5.5）

### 5.4 推定できない場合

次の場合は推定せず、`estimatedPosition = nil`（`.auto` なら `position` も nil = 未設定）のままにする。

- セッションにフィールドが紐付いていない（`fieldId == nil`、またはフィールドが見つからない）
- フィールド内に入る GPS 点が60点未満（約1分未満）

信頼度が低い場合でも、推定できる限り最も高いポジションを設定する（どのみちユーザーが確認・修正する前提のため、閾値を設けない）。

### 5.5 推定を行うタイミング

**`positionSource == .manual` のセッションの `position` は、どのタイミングでも変えない**（`estimatedPosition` は更新してよい。「自動推定に戻す」を選んだときに使うため）。推定したあとは §5.3 の WB ルールを適用し直す。

| タイミング | 処理 |
|---|---|
| セッション保存時（`saveSession`） | フィールドが紐付いていれば推定する |
| フィールドの紐付けが決まった・変わったとき（`autoAssignFieldId`、手動選択） | 推定し直す |
| コート入れ替え（`updateIsFlipped`） | 推定し直す。向きが逆だと CB と FW を取り違えるため |
| ドリル分割の確定（自動・手動とも） | 切り出した各セッションごとに推定する。分割元セッションのポジションは引き継がない |
| 過去セッションの一括計算（§7） | 未推定のセッションを推定する |

推定と同時に、§6 のポジションの高さも同じ GPS データから計算し直す（どちらもフィールドと `isFlipped` に依存するため）。

### 5.6 プロスタイル診断との関係

プロスタイル診断の判定ロジックは変えない（表記だけ §5.7 で変える）。推定には GK のテンプレートがあるため、診断が「CB」、ポジション推定が「GK」のように食い違うことがある。また、WB ルールや手動の設定によって、セッションのポジションと診断の表示が違うこともある。これらの食い違いは許容する（§13）。

### 5.7 プロスタイル診断の表記変更

`ProStyle.category`（と `PositionSyncResult.category`）を `String` から `PlayingPosition` に変え、表記を7分類にそろえる。診断画面での表示は次のとおり。

| 旧 category | 新 category | 診断画面の表示 |
|---|---|---|
| CF | `.fw` | FW |
| ウイング | `.wg` | **WG（WB）** |
| センターハーフ | `.mf` | MF |
| CB | `.cb` | CB |
| SB | `.sb` | **SB（WB）** |

- 「（WB）」を付けるのは、ヒートマップでは WB を見分けられず、WB の選手は SB か WG のどちらかに判定されるため。WB の選手がどちらの結果になっても違和感がないようにする
- 診断画面用の表示名は `PlayingPosition` の別プロパティ（例: `diagnosisLabel`）として持つ。ポジションのチップやバッジ（§4.3）は通常の表示名（SB・WG）を使う
- 判定ロジックへの影響はない（グループ分けのキーが文字列から enum に変わるだけ）

## 6. ポジションの高さ（新指標）

### 6.1 定義

「フィールドの縦方向で、自陣ゴールラインからどれだけ前にいたか」を、フィールドの長さに対する割合（0〜100%）で表す。0% = 自陣ゴールライン、50% = センターライン、100% = 敵陣ゴールライン。フィールドの大きさが違っても比べられるように、メートルではなく割合にする。

| 指標 | 定義 | 見えること |
|---|---|---|
| **平均の高さ** | フィールド内の全 GPS 点の高さの平均 | 普段どのあたりでプレーしているか（CB のラインの高さ、SB・WB の攻撃参加の度合い など） |
| **最前線の高さ** | 全 GPS 点の高さの95パーセンタイル | どこまで前に出ていったか（GK の飛び出し、CB の攻撃参加 など）。最大値だと GPS の誤差1点に引っ張られるため、95パーセンタイルを使う |
| **最低線の高さ** | 全 GPS 点の高さの5パーセンタイル | どこまで後ろに戻ったか（FW がどこまで守備に戻っていたか など）。最前線と同じ理由で、最小値ではなく5パーセンタイルを使う |

### 6.2 計算

`computeThirdRatios` と同じく、`field.convertToFieldCoordinate` で GPS 点をフィールド座標に変換し、`isFlipped` を反映した縦座標 `fy` を使う。

```
高さ(%) = clamp(fy / field.dimensions.length, 0, 1) × 100
```

- `convertToFieldCoordinate` が nil を返す点は除外する
- フィールド外の点（タッチラインの外・ゴールラインの外）は 0〜100% にクランプして含める（スローインやゴールライン際のプレーを落とさないため）
- 推定と同じく、使える点が60点未満なら計算しない（nil）

### 6.3 データモデル

```swift
var avgPositionHeight: Double?     // 平均の高さ（0…100%）
var frontPositionHeight: Double?   // 最前線の高さ（0…100%、95パーセンタイル）
var backPositionHeight: Double?    // 最低線の高さ（0…100%、5パーセンタイル）
```

### 6.4 評価の向き

高さは「高いほど良い」指標ではない（CB や GK が高ければ良いわけではない）。そのため推移画面・今日の出来カードでは、**順位や自己ベストの表示をせず、色による良し悪しの表現もしない**。「平均より前／後ろ」と差分（ポイント）だけを表示する。

## 7. 過去セッションの一括計算

推移グラフは過去のデータが揃っていることが前提だが、詳細画面を開いていないセッションは指標の一部が nil になっている。また、ポジションと高さは新しい項目なので、過去のセッションには値がない。そこで、アプリ起動時にバックグラウンドで一括計算する。

### 7.1 対象と条件

対象は `isSupersededBySplit == false` の全セッション。各項目は**それぞれ独立した条件**で判定する（ある項目の計算済みフラグに他の項目を相乗りさせない。sprintCount 同期漏れの再発防止）。

| 項目 | 計算する条件 |
|---|---|
| `staminaDrop` | nil |
| `hrIntensityRatio` | nil、かつプロフィールの年齢が設定済み |
| `sprintCount` | 現在の閾値で計算し直した値と異なる |
| `avgPositionHeight` / `frontPositionHeight` / `backPositionHeight` | 平均または最低線が nil、かつフィールドが紐付いている（最低線は後から追加したため、平均だけ計算済みのセッションも計算し直す） |
| `estimatedPosition` | nil、かつフィールドが紐付いている |

一括計算がすべて終わったら、§5.3 の WB ルールを全セッションに一度適用する。

どれも当てはまらないセッションは GPS データを読み込まずにスキップする。

### 7.2 処理

- 計算式は詳細画面と同じ関数を使う（`computeTimeSeries` → `computeStaminaDropRate`、`computeHeartRateIntensity`、`computeSprintSegments`）
- GPS データは1セッションずつ読み込み、使い終わったら手放す（12ヶ月分をまとめてメモリに載せない。LRU キャッシュにも入れない）
- 1セッション分を計算するたびにローカルに保存する（途中でアプリが終了しても、それまでの結果は残る）
- `staminaDrop`・`hrIntensityRatio`・`sprintCount` が変わったセッションは、詳細画面と同じく Supabase の `session_summaries` に再アップロードする。**アップロードには今計算した値を上書きしたコピーを使う**（値型の古いコピーを送るバグの再発防止）
- 詳細画面の既存の初回計算処理は残す（一括計算が終わる前に詳細を開いた場合のため）

## 8. 推移画面

### 8.1 入口

推移画面は専用の **Stats タブ**（`StatsView`）として置く（タブ順: Player Data／Stats／Sessions／Fields／Settings）。当初はプレイヤーデータタブの下部に入口カードを置く案だったが、見づらいため専用タブにした。あわせて、Player Data タブにあった「今回 vs 直近5回平均」の比較カードも Stats タブの一番上に移した。Player Data タブにはレベル・二つ名・レーダーチャート・バッジを残す。

開発用の Test タブは廃止した。中にあった開発者ツール（テストデータ生成・GPSログ・計測データ・閾値キャリブレーション集計・レーダーMax参考集計・全データ削除）は、Debug ビルドのときだけ設定画面の「開発者ツール」から開ける。

### 8.2 画面構成

```
GrowthTrendView
├── 期間: [1M] [3M] [6M] [12M]           ← セグメント。初期値 3M
├── ポジション: [すべて ▼]                ← メニュー。すべて / FW / WG / MF / CB / SB / WB / GK / 未設定
│                                           各項目に期間内の件数を表示（0件の項目は選べない）
├── 指標: [走力] [スプリント] [アジリティ] [最高速度] [高強度] [スタミナ] [立ち位置]  ← 横スクロールのチップ
├── 推移グラフ（§8.3）
└── 成長サマリー（§8.4）
```

選んだ期間・ポジション・指標は `@AppStorage` で覚えておく。

### 8.3 推移グラフ

Swift Charts で描く。

- **点:** 1セッション＝1点。横軸は日付、縦軸は指標の値
- **線:** 直近5回分の移動平均。3点以上たまった時点から描く。1回ごとのばらつきに埋もれず、傾向が見えるようにするため
- **自己ベスト:** 選んだポジション条件の中で、基準日時までの全期間の**有効値の中で一番高い記録**（同じ値なら古い方。最初の記録も対象）。期間の中にあれば、その点だけをオレンジの＊で強調する。さらに、その値を**オレンジの点線の横線**で常に示し、「自己ベスト 25.1（7/20）」のように値と日付を添える（期間の外の記録でも、どこが自分のベストか分かるようにするため）。参考値（§10.1）は使わない。「立ち位置」には付けない（§6.4）
- 点をタップすると、日付・値・プレー時間を表示し、セッション詳細に移動できる
- 12M でもセッション単位の点で描く（練習試合・試合のみを記録する前提なので、点が多くなりすぎない）
- 期間内に点が1つもない場合は「この条件のセッションはまだありません」と表示する

**指標と単位:**

| 指標 | 値 | 表示単位 | 備考 |
|---|---|---|---|
| 走力 | 総距離 ÷ プレー時間 | m/分 | |
| スプリント | スプリント回数 ÷ プレー時間 × 10 | 回/10分 | 1分あたりだと 0.7回 のような小さい値になり分かりにくいため10分あたり |
| アジリティ | アジリティターン数 ÷ プレー時間 × 10 | 回/10分 | 同上。`agilityTurnCount == nil` のセッションは点を出さない |
| 最高速度 | `maxSpeed × 3.6` | km/h | |
| 高強度 | `hrIntensityRatio` | % | nil は点を出さない |
| スタミナ | `staminaDrop × 100`（後半の運動量 ÷ 前半の運動量） | % | 表示名は「後半の運動量の維持率」。nil は点を出さない |
| 立ち位置（ポジションの高さ） | `avgPositionHeight`・`frontPositionHeight`・`backPositionHeight` の3本 | % | 3系列を同じグラフに描く（形でも区別: 平均＝丸、最前線＝三角、最低線＝四角）。nil は点を出さない。グラフの下に解説文を出す（下記） |

**立ち位置の解説文（グラフの下に表示）:**
> 自陣のゴールラインを0%、敵陣のゴールラインを100%として、フィールドの縦方向のどこでプレーしていたかを表します。50%がセンターラインです。

画面上の指標名は「立ち位置」とする（「高さ」だけでは何の指標か分かりにくいため。グラフの見出しは「立ち位置（ポジションの高さ）」）。

プレー時間で割る指標を基本にするのは、セッションごとにプレー時間が違うため（比較カードの「総距離＋プレー時間を併記」方針とは別に、長期の推移では時間あたりの値を使う）。

### 8.4 成長サマリー

期間内のセッションを日付順に並べて前半と後半に分け、指標ごとに平均を比べる。

```
成長サマリー（3ヶ月・MF・12回）
  走力         112 → 121 m/分   +8%
  スプリント   6.1 → 6.4 回/10分 +5%
  最高速度     27.2 → 27.0 km/h  −1%
  …
  平均の高さ   44 → 51%          5〜7ポイント前へ   ← 高さは差分（ポイント）で表示、色を付けない
```

- 期間内のセッションが6件以上（前半・後半それぞれ3件以上）あるときだけ表示する。足りないときは「6回以上の記録が貯まると表示されます」と表示する
- 件数が奇数のときは、真ん中のセッションを後半に含める
- 指標ごとに値がないセッションは、その指標の計算からだけ除く。その結果、前半・後半のどちらかが3件未満になった指標は「—」と表示する

## 9. 「今日の出来」カード

### 9.1 置き場所と比較対象

セッション詳細画面に置く。比較対象は次の条件をすべて満たすセッション。

- 表示中のセッションより前の日時である（表示中のセッション自身と、それより後のセッションは含めない。過去のセッションを開いたときも「その日の時点での」比較になる）
- 表示中のセッションの日時から遡って、選んだ期間内にある
- 表示中のセッションと同じポジションである（表示中のセッションのポジションが未設定なら、ポジションで絞り込まない）
- §10 の共通ルールを満たす

期間はカード上部のセグメント（1M／3M／6M／12M、初期値 3M）で切り替える。推移画面とは別に覚えておく。

### 9.2 表示

```
今日の出来（過去3ヶ月・MF・比較12回）
  走力       121 m/分   平均比 +9%   12回中 2位   [━━━░░▮░]
  スプリント 5.8 回/10分 平均比 −4%   12回中 8位   [━━▮░░░━]
  …
  平均の高さ 51%        平均より 6ポイント前
```

- **平均比:** 比較対象の平均に対する増減（%）
- **順位:** 比較対象に今回を加えた中での順位（「13回中2位」）。同じ値は同順位にする
- **分布バー:** 比較対象の最小〜最大を横線、25〜75パーセンタイルを帯で描き、今回の値をマーカーで重ねる
- 「高さ」は順位と分布バーを出さず、平均との差（ポイント）だけを表示する（§6.4）
- 指標ごとに、比較対象が3件未満なら「データ不足」と表示する
- 今回のセッション自身が §10 のルールで対象外（5分未満・平均から除外・分割で置き換え済み）なら、カード自体を出さない

## 10. 集計の共通ルール

推移グラフ・成長サマリー・今日の出来カードの**すべて**に適用する。

- 対象は `PlayerDataEngine.eligibleSessions` と同じ条件（5分未満・`isExcludedFromAverage`・`isSupersededBySplit` を除く）。今は `private` なので `internal` にして共通で使う
- ポジションで絞り込むときは、`position` の値で比べる。「未設定」を選んだときは `position == nil` のセッションを対象にする。「すべて」のときは絞り込まない
- 期間は「基準日時から N ヶ月前まで」とし、カレンダーの月単位で計算する（`Calendar.date(byAdding: .month, value: -N, to:)`）。推移画面の基準日時は現在、今日の出来カードの基準日時は表示中のセッションの日時
- 指標ごとの値がない（nil）セッションは、その指標の計算からだけ除く

### 10.1 GPS 精度の悪いセッションの最高速度は参考値

- **判定:** セッションの GPS 精度（`horizontalAccuracy`）の中央値が 10m より悪い（`TrainingSession.gpsAccuracyMedian` / `isLowGPSAccuracy`）。実データでは、良い日は 2〜4m、悪い日は14m前後とはっきり分かれた（例: 同じ「中外製薬」のフィールドで、7/04 は3m、悪天候で濡れた長袖の上から着けていた 10/24 は14m）
- **対象の指標:** 最高速度だけ。誤差がそのまま値を押し上げるため
- **扱い:** 値は消さず、推移グラフには**白抜きの丸**で描く（凡例「GPS精度が低い記録（参考値。平均・自己ベストには使わない）」）。**移動平均・自己ベスト・成長サマリー・今日の出来の比較には使わない**。今日の出来カードで今回が参考値なら、順位の代わりに「参考値（GPS精度が低い記録）」と表示する
- **採用しなかった案:** 精度が10mより悪い「点」の速度を最高速度の計算から外す案。精度の悪い日は全体が14m前後のため、たまたま精度が良かった数点（多くは歩いていたとき）しか残らず、最高速度が時速5〜10kmという実態とかけ離れた値になった。実質的にセッション単位で値を捨てるのと同じになるため採用しなかった
- **精度の計算:** 保存時（`saveSession`）と、起動時の一括計算（§7、`gpsAccuracyMedian` が nil のセッション）

### 10.2 精度の伝え方（2026-10-29決定・実装済み・実機確認済み）

> 競合ベンチマーク（`docs/競合ベンチマーク.md` §4の検討事項6）で決定。

**背景（調査）:** Apple WatchのGPSでサッカーの速度・距離の正確さを確かめた研究は見つからなかった。スポーツ用の腕時計8機種（Apple Watchを含む）の距離の誤差は平均3〜6%（ランニングで大きく、トラックでは良好）。専用端末（10Hz）でも、直線の距離の誤差は1〜2%程度だが、Polar Team Proの胸・背中の端末はサッカーの最高速度・走行距離について「正確とは言えない」という研究がある。どの端末も速く動くほど誤差が大きい。Apple Watchは約1秒ごとに位置を測るため、短いダッシュの最高速度は低めに出たり取りこぼしたりしやすい。一方、走行距離やヒートマップのように長い時間をまとめた値は誤差が平均されやすい。

**方針:**

- **着け方は安全を優先する。** プレー中は周りの選手の安全のため、リストバンドやサポーターでWatchを覆うことを勧める（「手首に直接着ける」とは勧めない。ユーザーの指摘による）。手元のデータで精度が下がったのは「雨で濡れた長袖の上から」着けた日で、悪かったのは濡れていたことの影響が大きいと考えられる（GPSの電波は水分で弱まりやすい。乾いた薄手のリストバンドの影響は未確認）
- 精度が下がったときは、§10.1の判定（アプリが自動で判定）でカバーする
- 専用端末と同時に測って誤差を公表する案は見送った（1人・数回の比較では根拠として弱く、他社製品と比べる表現は景品表示法の面でも注意が要る）

**表示:**

| 場所 | 内容 |
|---|---|
| セッション詳細のヘッダー | `isLowGPSAccuracy`のとき「GPSの精度が低い記録です」「最高速度は参考値で、スプリントの回数も誤差が出やすくなります。雨や汗でリストバンドが濡れると精度が下がることがあります」。タップでヘルプを開く |
| ヘルプ「数値の見方と着け方」（`ViewsMeasurementHelpView.swift`、設定のサポートと上の表示から開く） | プレー中の着け方（リストバンドで覆う、公式戦では外すのが一般的）、GPSの精度について、目安として信頼しやすい数値（走行距離、ヒートマップ、サードの割合、時間帯別の運動量）、誤差が出やすい数値（最高速度、スプリントの回数）、おすすめの使い方（自分の変化を見る）、精度を上げるコツ（振動で位置が決まるのを待つ、屋根の下や高い建物の近くを避ける） |
| App Storeの説明文の「ご注意」 | 「プレー中は、周りの選手の安全のため、リストバンドなどでApple Watchを覆ってください」を加える（`docs/競合ベンチマーク.md` §6.4） |

**実機確認（2026-10-29）:** 設定の「数値の見方と着け方」、精度の低い記録のセッション詳細の表示と、タップでヘルプが開くことを確認した。

**任意の確認:** いつもの練習で、乾いたリストバンドで覆った日の記録が「精度が低い記録」にならなければ、覆っても問題ないと言える。

## 12. テスト

`FootballGPSTests` に追加する。

**ポジション推定・高さ（`SessionDataManager`）**
- 自陣ゴール前だけに点を置いた合成 GPS データ → GK と推定される
- 中央縦長に点を置いたデータ → MF と推定される
- 敵陣ゴール前の中央に点を置いたデータ → FW と推定される
- 同じデータで `isFlipped` を反転させる → GK と FW が入れ替わるなど、向きが反映される
- フィールド内の点が60点未満 → nil
- 推定結果が WB になることはない

**WB ルール**
- 前に手動で WB を設定したセッションがある場合、推定 SB・WG → WB、推定 MF → MF のまま
- 手動 WB のあとに手動 CB を設定した場合、それより後の推定 SB → SB のまま
- 手動で設定したセッションより前の日時のセッションには、ルールが働かない
- 手動の設定を変えると、GPS データを読み込まずに後のセッションの `position` が更新される
- 手動で設定したセッションの `position` は、ルールでも推定でも変わらない

**表記**
- `diagnosisLabel`: SB → 「SB（WB）」、WG → 「WG（WB）」、ほかは表示名のまま
- 高さ: センターラインだけに点を置く → 平均・最前線とも約50%。フィールド外の点は 0〜100% にクランプされる

**集計（`GrowthTrendEngine`）**
- 期間の境界（ちょうど N ヶ月前のセッション）の扱い
- ポジションでの絞り込み（すべて・特定ポジション・未設定）
- 5分未満・平均から除外・分割で置き換え済みのセッションが、すべての集計から除かれる
- 移動平均が3点目から始まり、5点の窓で計算される
- 前半後半比較: 5件 → 表示しない、6件 → 3件ずつ、7件 → 3件と4件
- 順位: 同じ値が同順位になる
- 今日の出来: 表示中のセッションより後のセッションが比較対象に入らない

**一括計算**
- `positionSource == .manual` のセッションのポジションが変わらない
- `staminaDrop` 計算済みで `sprintCount` だけずれているセッションも同期される
